# Data layer

Two tables, both with host-configurable names (`config-sso.tables.*`).

## `sso_providers`

One row per configured identity provider. Modelled by `Models\SsoProvider`.

| Column | Type | Notes |
|---|---|---|
| `id` | bigint | Primary key |
| `uuid` | string | Auto-generated by the `HasUuid` trait |
| `name` | string | Display name (e.g. "GitHub") |
| `driver` | string | Socialite driver key (`github`, `keycloak`, …) |
| `client_id` | string | OAuth client id |
| `client_secret` | **text** | **Encrypted** at rest (`encrypted` cast) |
| `redirect_url` | string, nullable | Overrides the derived callback URL when set |
| `config` | json | Driver-specific extra fields (`instance_url`, `base_url`, `realms`, `tenant`, …) |
| `is_active` | boolean | Gated by the `active()` scope |
| `show_logo` | boolean | Render the provider logo on the button |
| `sort_order` | integer | Login-button ordering |
| `icon` | string, nullable | Icon name or logo URL |
| `button_label` | string, nullable | Custom button text |

Key methods:

- `scopeActive()` — `where('is_active', true)`.
- `getRedirectUrl()` — `redirect_url` if set, else `route('sso.callback', $driver)`.
- `toSocialiteConfig()` — builds the runtime `services.{driver}` array (`client_id`,
  `client_secret`, `redirect`) merged with the `config` JSON.

## `sso_user_providers`

Links a local user to a provider identity. Modelled by `Models\SsoUserProvider`.

| Column | Type | Notes |
|---|---|---|
| `id` | bigint | Primary key |
| `user_id` | bigint | Indexed; references the configured user model |
| `sso_provider_id` | bigint | Indexed; references `sso_providers` |
| `provider_user_id` | string | The user's id at the IdP |
| `email` | string | Email returned by the IdP |
| `token_data` | **text** | **Encrypted** `{ token, refresh_token, expires_in }` |

`user()` resolves the host's authenticatable from `config('config-sso.user_model')`.

## Gotchas

**Encrypted columns must be `text`, never `json`/`jsonb`:**

> The `encrypted` cast stores an opaque string; PostgreSQL rejects that as invalid JSON (SQLite passes
> silently). This applies to both `client_secret` and `token_data`.

**No foreign-key constraints** on `user_id` / `sso_provider_id`:

> The users and providers table names are host-configurable, so the migrations use plain indexes
> instead of FKs.

The workbench migrations `require` the package's `.php.stub` migration files so the demo schema can
never drift from what ships.
